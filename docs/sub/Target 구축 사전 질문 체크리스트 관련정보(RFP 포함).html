구축 가이드

★ 구축 가이드라인 — 웹·앱 가능 경로(권장/대안) + 1st-party 간판

RFP 무과금 = 고객사 소유 호스트(SNI) 필수. 웹·앱 모두 권장(Edge) / 대안(클래식 Target Delivery) 두 문을 연다. 상세 스니펫은 사전배경 ③·도메인 절차는 부록.

한 줄 스탠스 · 근거 등급
  • 권장 · 근거 확실 — 웹 alloy + 앱 Edge/Optimize. 간판 키(edgeDomain/edge.domain)에 “first-party domain” 공식 문구 + Adobe-Managed Certificate
  • 대안 · 웹 확실 / 앱은 추론+검증 — 웹 at.js는 Target CNAME HOWTO에 serverDomain 적용이 명시. 앱 클래식은 호스트 오버라이드 키 target.server는 공식이나, CNAME HOWTO·무과금은 모바일 적용 스텝이 없음 → Delivery API·소스상 동일 호스트 호출은 가능하나 PoC·AE 확인 전 “무과금 확정”으로 쓰지 말 것
  • CNAME 프로그램이 둘로 갈림: Edge Managed Cert(*.data.adobedc.net) vs Target CNAME(*.tt.omtrdc.net). Adobe가 혼용을 기술 차단한다고 적힌 문서는 없음 — 다만 통신사 규칙·인증서 이중 운영상 한 세트로 맞추는 것을 권장

↓

↓

↓
⑤ Rule로 개인화 요청 (아래 런타임) — Target 확장·Load Target 불필요

④ HTML에 넣는 것 = Tags install만 (Web SDK가 alloy를 올림)

2-② 런타임 — 갈래 A-1 자동 렌더 (FE 커스텀 최소)

페이지 로드 → Tags install 실행 → Web SDK 준비
↓
Rule (예: Library Loaded / DOM Ready) → Send event renderDecisions: true · decisionScopes 또는 페이지 범위
↓
Edge→Target 응답 → SDK가 HTML 오퍼를 DOM에 적용 (VEC式) FE가 JSON 파싱·컴포넌트 렌더를 안 해도 됨
// Tags Rule 액션이 같은 API를 호출. 개념 코드:
alloy("sendEvent", {
  renderDecisions: true,   // ← SDK가 DOM에 자동 적용
  xdm: { web: { webPageDetails: { name: "home", URL: location.href } } }
});
// FE 추가 렌더 함수 없음 (HTML/VEC 오퍼 전제)

2-③ 런타임 — 갈래 A-2 헤드리스 JSON (이번 RFP·인사이더式 · FE 개발)

페이지 로드 → Tags install → Web SDK 준비
↓
Rule 또는 프론트 코드 → sendEvent renderDecisions: false · decisionScopes: ["home-hero"]
↓
응답 propositions[].items[].data.content = JSON
↓
FE 개발 코드가 JSON 파싱 → React/Vue/자체 컴포넌트 렌더
// (1) Tags Custom Code / 페이지 스크립트 — 요청
alloy("sendEvent", {
  renderDecisions: false,              // ← 자동 DOM 적용 OFF
  decisionScopes: ["home-hero"],     // Target location / mbox 이름
  data: {
    __adobe: { target: { "profile.loginStatus": "logged-in" } }
  }
}).then(function (result) {
  // (2) FE가 미리 만들어 둔 렌더 함수
  (result.propositions || []).forEach(function (p) {
    (p.items || []).forEach(function (item) {
      if (item.data && item.data.content) {
        renderHero(p.scope, item.data.content);  // ← 프론트엔드 개발
      }
    });
  });
});

// (3) FE 쪽 예시 (별도 번들)
function renderHero(scope, json) {
  // json = Target JSON Offer 페이로드
  document.querySelector("[data-mbox="+scope+"]").innerHTML =
    "<h2>"+json.title+"</h2><p>"+json.text+"</p>";
}
W-A 핵심 — Tags에 넣는 것은 Web SDK 확장+install. Load Target Rule 없음. FE 코드는 A-2(헤드리스)일 때만 필수. 간판은 확장의 Edge domain / edgeDomain.

3-③ 런타임 — 갈래 B-2 헤드리스 JSON (FE 개발)

install → Load Target 완료 후
↓
FE/Custom Code → adobe.target.getOffers(...)
↓
응답 mbox options[].content = JSON
↓
FE 개발 코드가 파싱 → 자체 컴포넌트 렌더
// Load Target 이후 (Rule Custom Code 또는 페이지 번들)
adobe.target.getOffers({
  request: {
    execute: { mboxes: [{ index: 0, name: "home-hero" }] }
  }
}).then(function (res) {
  var opt = res.execute.mboxes[0].options || [];
  var json = opt[0] && opt[0].content;
  if (json) renderHero("home-hero", json);   // ← 프론트엔드 개발 (A-2와 동일 역할)
});

function renderHero(scope, json) {
  document.querySelector("[data-mbox="+scope+"]").innerHTML =
    "<h2>"+json.title+"</h2><p>"+json.text+"</p>";
}
W-B 핵심 — Tags에 Adobe Target 확장 + Rule에 Load Target이 있음. FE 코드는 B-2(헤드리스)일 때만 필수. “B는 FE 불필요”는 B-1(자동 적용)에만 해당.

사전 배경 ②

헤드리스 JSON 아키텍처 & 개발사 스코프 정의

이번 프로젝트의 성격을 규정하는 두 전제 — 구현 아키텍처(헤드리스)와 개발 범위.

① 주요 오퍼를 JSON으로 주고받는 "헤드리스" 방식

  • 웹·앱 모두 SDK로 구축, 타겟은 "콘텐츠 결정(decisioning)"만 담당
  • 렌더링은 자사/고객 프론트·네이티브 컴포넌트가 수행 (VEC로 DOM 직접 변경 안 함)
  • 결과 → DOM 셀렉터·flicker 비중 ↓, JSON 스키마·렌더 컴포넌트 준비도가 핵심

Q1. Web SDK/데이터스트림을 쓰려면 AEP(Experience Platform)를 구매해야 하나요?
웹(W-A): 공식 FAQ — Web SDK 사용에 AEP/RTCDP 구매 불필요. 데이터스트림에 Target 서비스만 켜도 동작. RTCDP·CJA 등은 별도.
앱 Edge(M-A): Event Schema·데이터스트림 구성이 가이드상 선행. Dataset은 데이터스트림에서 AEP(Experience Platform) 서비스로 적재할 때 필요(Target만 ON이어도 스키마 선택은 통상 필요). Target 단독 계약으로 Platform UI/적재가 되는지는 AE 확인. allow list 가능.
앱 클래식(M-B): 데이터스트림·XDM 스키마 불요 — Target clientCode + Identity + Target 확장.
Q2. XDM 스키마를 반드시 정의해야 하나요?
경로별 다름.
웹(alloy) — Target 파라미터는 data.__adobe.target으로 XDM 스키마 없이 가능(공식 data 객체).
앱 M-A(Edge+Optimize) — Edge로 보내는 experience 데이터는 XDM 객체가 기본. “비XDM 객체 미지원”은 Edge 수집 가이드 문구. 다만 Optimize는 Target 파라미터를 data 딕셔너리로도 보낼 수 있음(학습 가이드). 스키마 정의는 통상 필요 · Dataset은 AEP 적재 시.
앱 M-B(클래식 Target) — mbox/profile 파라미터 맵 — XDM 스키마 불요.
Q3. "SDK 구축"은 곧 서버사이드 작업인가요?
아니요. at.js·alloy·모바일 SDK는 모두 클라이언트사이드. 서버사이드 Delivery는 별축.
Q4. at.js / 앱 클래식은 못 쓰나요? 무과금은?
제품 지원: 둘 다 지원·동작. 권장 제안은 W-A+M-A.
무과금 간판: 웹 W-A·W-B는 공식 문서가 닫힘. 앱 M-A도 edge.domain first-party 문구로 닫힘. 앱 M-B는 target.server 호스트 지정까지 공식 · CNAME/무과금은 문서 공백 → PoC·AE 전 “확정 가능”으로 말하지 말 것 (★·부록).
Q5. 반드시 Tags(데이터 컬렉션)로만 넣어야 하나요?
필수는 아닙니다(HTML/앱 직접 삽입·SDK 가능). 운영·환경 분리상 Tags 권장 → A-1.

부록 — 1st-party 도메인 구성 흐름 (요약)

RFP상 요구되는 1st-party 도메인(CNAME) 구성 원리·설정·흐름. 공식문서 근거.

한 줄 개념 (비유)

Adobe 서버(임대 건물)는 주소(IP)가 수시로 바뀜 → 통신사가 고정 IP로 무과금 처리할 수 없음.

대신 그 건물 앞에 우리 회사 간판(1st-party 도메인)을 달면, 통신사는 그 간판(도메인=SNI)을 보고 무과금 처리.

왜 Adobe 공용 도메인(clientCode.tt.omtrdc.net 등)은 안 되나

  • 기본 호출 호스트 예: at.js <clientCode>.tt.omtrdc.net · Edge Network edge.adobedc.net / *.data.adobedc.net
  • clientCode가 고객마다 달라도 여전히 Adobe 소유 apex(tt.omtrdc.net / adobedc.net) — "우리 서비스 도메인"이 아님
  • 통신사 무과금은 요청의 간판 도메인(SNI)을 보고 판단 → 등록 대상은 보통 고객사(당사) 소유 도메인. Adobe 벤더 공용 도메인을 무과금 목록에 넣는 방식은 RFP 취지·운영과 맞지 않음
  • 그래서 CNAME으로 고객사 도메인(예 data.회사.com)을 Adobe에 연결하고, SDK에는 그 도메인을 지정 → 통신사가 보는 간판 = 고객사 도메인
한 줄 정리 — clientCode는 Target 계정 식별용이지, 통신사에 올릴 "우리 간판"이 아님. 통신사에 올릴 간판은 고객사 1st-party 도메인이어야 함.

용어 — 프로그램을 섞지 말 것

  • 1st-party 도메인 — 고객사 소유 서브도메인(예 data.회사.com · target.회사.com). apex(회사.com)는 기존 DNS와 충돌 위험이 커 Target CNAME FAQ도 서브도메인 권장.
  • 프로그램 A — Adobe-Managed Certificate — Edge/데이터 수집용. CNAME 타깃 예 xxxx.data.adobedc.net. SDK 키: 웹 edgeDomain · 앱 edge.domain.
  • 프로그램 B — Target CNAME — Target Delivery용(별도 호스트·인증서). CNAME 타깃 예 xxxx.tt.omtrdc.net. SDK 키: 웹 at.js serverDomain(공식 HOWTO) · 앱 target.server(호스트 오버라이드 공식, CNAME 연계는 추론).
  • Analytics CNAME과 Target CNAME도 호스트·인증서 공유 불가(Target FAQ). Edge Managed Cert ≠ Target CNAME.
